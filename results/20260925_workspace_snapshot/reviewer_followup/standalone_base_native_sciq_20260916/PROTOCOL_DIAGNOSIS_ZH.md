# 为什么 Base 需要重新核对结束符

这个诊断发生在最初 ChatML 方案的验证调参阶段，没有使用该轮测试分数。旧尝试记录在 `../standalone_base_sciq_20260916`，已中止并封存；纠正方案的适配器全部重新初始化。

对经过官方哈希核验的原始词表权重逐行比较发现：

| 官方 Base checkpoint | 与 im_end (151645) 完全相同的行数，含其自身 | 与原生 EOS (151643) 完全相同的行数 |
|---|---:|---:|
| Qwen3-0.6B-Base | 291 | 1 |
| Qwen2.5-1.5B | 267 | 1 |

若冻结输出矩阵的两行满足 `W_i = W_j`，则对任意隐藏表示 `h`，都有 `W_i h = W_j h`。只训练输入侧适配器或内部 LoRA 可以改变 `h`，却不能打破这个等式。输出侧共享仿射映射同样满足 `W_i (I+A) = W_j (I+A)`，仍然不能区分这些行。本轮没有独立的可训练词表行偏置。

因此，若目标 token 属于包含 K 个相同行的集合，它的 softmax 概率不超过 `1/K`，对应单 token CE 不低于 `log(K)`。本例中存在编号小于151645的相同行，常规取首个最大值的 greedy argmax 也不能单独选中151645。这是当前冻结输出矩阵下的结构限制，不能通过给上述适配器更高学习率解决。

这不意味着所有 Base 模型的 ChatML token 都如此，也不意味着必须更新整个 Base。对本次两个 checkpoint，直接采用独立的原生 EOS151643即可解除该监督目标的不可区分性。本轮同时采用不含 chat 特殊 token 的文本补全提示，并核对每条提示和答案的分词拼接。

这个修正改变了输入和停止协议。因此，纠正后的 Base 结果与旧 Instruct 结果仅作背景对照；不能把差异单独归因于模型训练阶段。主比较是本轮同一 Base、同一补全协议下的未适配模型、单侧 A-LoRA 和独立的内部 LoRA。

完整相同行编号见 `BASE_SPECIAL_TOKEN_DIAGNOSTIC.json`；模型来源与哈希见 `MODEL_PROVENANCE.json`；纠正后的预定训练和检验规则见 `DESIGN.md`。
