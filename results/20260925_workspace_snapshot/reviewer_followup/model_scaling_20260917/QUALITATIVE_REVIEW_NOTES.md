# 固定样例复核记录

本文件完成 3B/7B CLUENER seed 6100 和 3B/7B WikiSQL seed 7100 的固定样例检查，共16例。这是各条件首个预定种子的描述性复核，不能代替五种子统计。选择规则与 `content_diagnostics.py` 一致：按固定测试顺序取最先两个叠加相对预算组的主任务正确胜例、两个败例（NER使用整句完全正确）；不改变训练或评分，也不用于估计胜败率。

## CLUENER / 3B / seed 6100

- `cluener_dev_1289`：预算组把“中国人民大学行政管理学研究所”分成两个组织实体；叠加组恢复与标注一致的完整机构跨度，人物与职位均保留。这是实体边界变化，两边 JSON 均有效。
- `cluener_dev_829`：预算组额外把“一方好砚”标成书名；叠加组只抽取人名“火来胜”，与标注一致。这是减少误报。
- `cluener_dev_495`（败例）：叠加组将游戏实体从“《魔兽世界》”错误延长至后面的“(下称“”，预算组跨度正确。输入本身在引号处截断，但该输入是原始数据文本，不是本轮 tokenizer 截断；不得据结果删除。
- `cluener_dev_93`（败例）：叠加组额外把“中国内地邮票”标成书名；预算组只输出标注的政府与公司两个实体。这是多报，并非格式错误。

首种子描述性计数：预算组 TP=1983、预测实体3130，叠加 TP=2082、预测3173，共3072个gold实体。预算/叠加 precision=63.35/65.62、recall=64.55/67.77；双方schema都有效的1322条上，F1=64.68/67.12。此子集由两组输出共同决定，不能作因果分解。逐类别有9类F1提高，game下降；所有类别及负例都要保留，不能据此泛化到全部种子。

## WikiSQL / 3B / seed 7100

- `wikisql-test-995`：预算组把“whatever size”错误加成面积等于“whatever”的过滤条件；叠加组去掉该条件，执行答案正确。不过叠加预测的COUNT列为Name，gold为Area，逻辑形式并不相同。这同时说明执行一致不能代替普遍的查询等价性判断。
- `wikisql-test-14566`：预算组把5,534生成为 `[1,2,5,534]`，条件包含四个元素，违反schema；叠加正确生成为 `[1,2,5534]`。这是数值表达和查询结构改进，不应把这个例子单独说成纯语义提升。
- `wikisql-test-4260`（败例）：叠加组把IL-1β的过滤条件放在Receptor列，而gold和预算组使用Name列；两边查询结构均有效，是列选择错误。
- `wikisql-test-6180`（败例）：叠加组把145,790生成成条件中的两个数值，得到四元素条件；预算组生成145790，查询正确。与第二条相反，这里叠加发生数值格式/结构退化。

首种子叠加相对预算组净多17题正确，其中双方query都有效的1017题贡献净多16题，其余三个有效性分层合计净多1题。净差可以相加回执行正确率，但按模型输出分层仍不是因果分解。严格JSON和有效查询不是同一指标；JSON语法正确的四元素条件也可违反查询schema。官方执行与独立占位符版本在该种子三组的总分相同。

## CLUENER / 7B / seed 6100

- `cluener_dev_955`：预算组只抽取第一次“暴雪”，叠加组同时恢复第二次出现并标为occurrence=1，原始跨度均与gold一致。这是实际的漏抽恢复，不是仅修复JSON。
- `cluener_dev_659`：预算组在“美国军方”之外又预测occurrence=0的“美国”地址，叠加组去掉这一gold未标的嵌套实体，其余两项一致。这里的正确指符合该数据的标注约定，不能从中推出“美国不是地名”等一般语义结论。
- `cluener_dev_1186`（败例）：叠加组把两个完整职位“营销总监”“策划总监”都缩成“总监”，并都赋occurrence=0；预算组按原始跨度正确恢复两项。叠加并不总能正确处理边界和重复出现。
- `cluener_dev_801`（败例）：叠加组把“达芬奇的工作间”标成scene，漏掉gold的人名“达芬奇”；预算组人名及另外两个实体正确。仍按固定跨度/类别规范计分，不事后更改标注。

首种子预算/叠加TP=2151/2188，预测实体3222/3138；precision=66.76/69.73，recall=70.02/71.22。双方schema有效的1324条上F1=68.69/70.72。该种子主要同时减少误报并增加少量正确实体，与3B首种子的预测实体数增加并不完全相同；不可据单种子建立统一机制解释。

## WikiSQL / 7B / seed 7100

- `wikisql-test-11915`：目标标题字符串本身含引号。预算组的值为 `parting glances`，叠加保留值内部的双引号，与gold和数据库匹配。两边JSON与查询结构均有效；这里是条件值的准确复制。
- `wikisql-test-2434`：预算组直接选择Natural Increase，叠加使用COUNT聚合，与该题gold一致。原问题措辞不自然，因此此例只说明对固定数据标注/执行目标的匹配，不作更强的人类语义断言。
- `wikisql-test-2724`（败例）：叠加把East Tennessee State过滤在Conference列，预算组和gold使用Regular Season Winner列。两边查询有效，是条件列错误。
- `wikisql-test-3067`（败例）：叠加把B. Ajith Kumar过滤在Name of Film列，预算组和gold使用Awardee(s)列。同样是条件列错误。

首种子叠加相对预算组净多16题正确。双方query都有效的1023题贡献净多17题，叠加额外1条无效查询贡献−1题。因此净增并非来自更高的格式有效率；三组严格JSON均100%，预算query有效100%，叠加99.902%。逻辑形式匹配从预算75.391%提高到叠加77.051%。官方执行与独立占位符版本在该种子三组的总分相同。

## 解释边界

这些固定胜败例涉及实体跨度、重复出现、条件列、条件值、聚合及数值表示。它们说明主指标覆盖了真实的内容差异，也展示了叠加仍会出错；不证明一个统一的内部机制，这是本次助手基于输入、gold与输出的逐例分析，不是独立人类评测，也不替代对全部预测和所有种子的复核。
